# 为什么聊天记录越长，Agent 反而越不聪明

## 问题

把完整聊天记录每次都发给大模型，看起来像是在提供更多信息，
实际会带来更高的成本、更长的延迟和更多旧话题干扰。

上下文工程不是把所有历史都塞进模型，而是决定：

- 哪些信息必须完整保留。
- 哪些旧消息可以压缩成摘要。
- 哪些内容可以从数据库或工具重新获取。

## 最小实验

在 OfferFlow 中构造 100 轮模拟对话，共 200 条 user 和 assistant 消息。
设置 6000 token 总预算，最近最多保留 20 条完整消息，其余旧消息交给摘要。

压测命令：

```powershell
cd D:\code\api
D:\code\api\.venv\Scripts\python.exe context_demo.py
```

单次运行结果：

```text
原始历史消息数：200
被摘要消息数：180
最近完整消息数：20
原始估算 token：3495
最终估算 token：481
预算：6000
100 轮上下文压测通过
```

## 取舍

代码负责确定性的上下文管理：

- 清洗非法角色和空消息。
- 限制单条消息长度和历史总量。
- 根据 token 预算选择最近消息。
- 保证 system 消息位于开头、当前问题位于末尾。

大模型只负责把较早的对话改写成事实摘要。压测里的摘要使用固定假函数，
因此 481 token 只证明预算和组装机制有效，不能代表真实摘要质量。

## 当前限制

- 还没有验证真实摘要是否保留全部关键事实。
- 当前没有持久化滚动摘要，超过窗口后会重新生成。
- 还没有把工具结果和后续 RAG 片段纳入同一套预算实验。

## 下一步

- 用真实 DeepSeek 摘要测试多轮岗位状态更新。
- 检查摘要是否保留目标城市、岗位方向、截止时间和未完成事项。
- 将摘要和最近消息持久化，避免每次请求重复总结整段旧历史。
